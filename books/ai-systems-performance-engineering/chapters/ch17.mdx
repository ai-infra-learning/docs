## 本章概要

分离式推理把一次请求交给多个执行单元，扩展能力取决于**状态交接与资源生命周期**：谁选择下一阶段的 Worker，谁分配目标内存，谁确认数据可读，以及谁在失败后回收资源。

- **PD 分离**在 Prefill 与 Decode 之间交接 KV Cache。
- **多模态 EPD 分离**增加编码阶段与 embedding 交接。
- **Attention–FFN 分离（AFD）**在逐层执行过程中反复交换中间激活。

## 引擎与 KV 传输层的衔接

### vLLM Connector 的调度契约

vLLM 的 [KVConnectorBase_V1](https://github.com/vllm-project/vllm/blob/7a64fb8fc9239cb65e0df9313fa759594dfb206a/vllm/distributed/kv_transfer/kv_connector/v1/base.py) 把外部 KV 的可用性接入调度器，再把物理块和传输任务交给 Worker。一次“外部命中”包含两个不同判断：外部是否存在可复用内容，以及这些内容是否已装入本次请求可用的 GPU 块。

| 接口 | 交接的信息 | 对请求生命周期的影响 |
| --- | --- | --- |
| `get_num_new_matched_tokens` | 本地已计算部分之外，外部还能提供多少 token；是否异步加载 | 调度器区分需要计算与等待加载的部分；返回 `None` 时稍后重试查询 |
| `update_state_after_alloc` | 已分配的目标块与外部 token 数 | Connector 获得本次加载的落点，不能只凭块列表是否为空判断是否需要传输 |
| `build_connector_meta` | 当前调度步对应的传输元数据 | Scheduler 与 Worker 对同一批传输任务建立关联 |
| `request_finished` | 计算结束后是否仍需保留块 | 异步发送未完成时继续持有源块 |
| `get_finished` | 已完成发送或接收的请求 | 调度器推进等待中的请求，或释放被传输占用的块 |

例如，Prefill 已经算完一个请求，源 KV 仍可能被远端 Decode 读取。`request_finished` 可以要求延迟释放，直到完成通知到达。若在计算结束时立即把这些块分配给新请求，远端读取就可能遇到被覆盖的数据。

同样，Decode 分配目标块只代表容量预留成功。接收完成之前，Attention 不能使用这些块；失败的加载需要向调度器反馈，而不能把部分有效的数据当成完整命中。

<Note>
**计算完成、传输完成、内存可回收，是三个不同的状态。** 源块和目标块的释放都需要与在途操作协调。
</Note>

### NIXL Pull 与 Push

[NIXL](https://github.com/ai-dynamo/nixl) 提供内存注册、传输描述与异步数据搬运能力。vLLM Connector 把请求的逻辑 token 范围映射到物理 KV 块，并决定何时提交传输、何时通知调度器。底层支持 RDMA，并不自动解决上层的请求配对和块生命周期。

[NIXL Pull 路径](https://github.com/vllm-project/vllm/blob/7a64fb8fc9239cb65e0df9313fa759594dfb206a/vllm/distributed/kv_transfer/kv_connector/v1/nixl/pull_worker.py) 由 Decode 使用源端元数据发起 `READ`；[Push 路径](https://github.com/vllm-project/vllm/blob/7a64fb8fc9239cb65e0df9313fa759594dfb206a/vllm/distributed/kv_transfer/kv_connector/v1/nixl/push_worker.py) 由 Prefill 向 Decode 已注册的目标位置发起 `WRITE`。

<Frame caption="来源：[vLLM — Push-based KV Transfer with NIXL](https://vllm.ai/blog/2026-10-14-nixl-push-connector)。">
  <img src="/books/ai-systems-performance-engineering/images/ch17-nixl-pull-vs-push.png" alt="NIXL Pull 与 Push 中 Prefill、Decode 分配及传输时序的比较" />
</Frame>

| 维度 | Pull | Push |
| --- | --- | --- |
| 发起数据操作的一侧 | Decode 读取 Prefill KV | Prefill 写入 Decode KV |
| 传输启动的前提 | D 获得源信息并准备本地接收块 | P 已生成 KV，且已获得 D 的目标块注册信息 |
| D 的选择时机 | 可以在 P 返回交接信息后选择 | 为提前注册目标空间，需要更早确定 D |
| 资源权衡 | 源 KV 等待后续 D 读取 | D 提前保留目标空间，P 将就绪数据推送过去 |

- **早选 D**：目标分配和注册可以与 P 的工作重叠，D 的 KV 容量也会在真正开始生成之前就被占用。
- **晚选 D**：可以利用更新的负载信息，但接收端准备工作可能落在 Prefill 之后。

实际收益取决于请求时序与可重叠的工作量。

<Frame caption="来源同上；实现细节见 [NIXL Push Connector 设计](https://github.com/vllm-project/vllm/blob/7a64fb8fc9239cb65e0df9313fa759594dfb206a/docs/design/nixl_kv_push_connector.md)。">
  <img src="/books/ai-systems-performance-engineering/images/ch17-nixl-push-flow.png" alt="Push 路径中的目标块注册、Prefill 计算、后台写入和完成通知" />
</Frame>

Push 的目标注册与 KV 计算可能按任意顺序完成。发送侧需要按请求标识匹配二者，再由后台写入线程提交传输；不能假定收到注册信息时，计算结果已经就绪。超时清理还必须与在途传输协调，避免旧请求的写操作落到已被重新分配的目标块上。

### Mooncake 的直接传输与共享存储

[Mooncake Transfer Engine](https://github.com/kvcache-ai/Mooncake/blob/6a835cbf934aa50c287261f255c83e6faffecb71/docs/source/design/architecture.md) 用 Segment 表示远端可访问地址空间，用 BatchTransfer 表示一组异步读写。元数据服务或点对点握手交换内存位置与连接信息，数据在持有源、目标缓冲区的进程之间传输。

vLLM 中的 [MooncakeConnector](https://github.com/vllm-project/vllm/blob/7a64fb8fc9239cb65e0df9313fa759594dfb206a/vllm/distributed/kv_transfer/kv_connector/v1/mooncake/mooncake_connector.py) 对接这条直接传输路径：注册 KV 区域，交换 Worker 与布局信息，把逻辑块展开成实际传输区域。布局元数据需要表达层、KV group、块大小和偏移；相同 token 数并不保证两个实例的物理 KV 排列相同。

[Mooncake Store Connector](https://github.com/vllm-project/vllm/blob/7a64fb8fc9239cb65e0df9313fa759594dfb206a/vllm/distributed/kv_transfer/kv_connector/v1/mooncake/store/connector.py) 则连接共享对象池。Store Master 管理对象位置、分配、租约与副本状态，Client 通过 Transfer Engine 搬运对象数据。前者处理两个引擎之间的交接，后者让 KV 的保存期限与计算 Worker 的请求期限分开。

### LMCache 与 MultiConnector

[LMCache 的 MP 分离式 Prefill 示例](https://github.com/LMCache/LMCache/blob/6913259264dbebb2fa5ba1665606c40ffc5c6661/docs/source/mp/disaggregated_prefill.rst) 使用 `MultiConnector` 组合两条路径：`NixlConnector` 负责本次请求的 P→D KV 交接，`LMCacheMPConnector` 负责引擎与独立 LMCache Server 之间的保存、查询和恢复。

Prefill 侧按本地 GPU Cache、LMCache、重新计算的顺序获取 KV。一次请求结束后，保存到 LMCache 的前缀仍可服务后续请求，即使引擎 HBM 中的副本已经被淘汰。该示例为 P、D 分别部署 LMCache Server；跨服务器复用需要另行配置 P2P 与协调服务。

这组组合适合解释 Connector 的两种任务：**当前请求需要完成状态交接，后续请求需要保留可复用状态。** 两者可以共享数据传输基础设施，但完成条件、保存期限与失败处理不同。当前 MP 示例还依赖 vLLM 的 MultiConnector 实际块传递修复，部署版本应按示例要求核对，不能直接沿用早期 in-process LMCache 的配置。

## KV 的存储、复用与生命周期

### 本地前缀与外部副本

<Frame caption="原书图 17-5。该图表达层级复用关系；具体存储后端和复制策略由部署决定。">
  <img src="/books/ai-systems-performance-engineering/images/ch17-figure-5.png" alt="KV 在 GPU、CPU 与存储层级中复用和迁移" />
</Frame>

引擎本地 Prefix Cache 保留已计算的前缀块，新请求匹配后可以直接复用 HBM 中的状态。外部 KV Cache 把复用范围扩展到引擎本地容量之外，但需要付出查找、加载和必要的布局转换成本。把数据保存在 CPU 或远端，并不等于下一次请求已经获得一次低成本命中。

| 机制 | 状态归属 | 请求结束后的状态 | 再次使用时的代价 |
| --- | --- | --- | --- |
| 引擎本地 Prefix Cache | 当前引擎的块管理器 | 符合缓存规则的块可继续保留，受本地容量限制 | 本地查找与块复用 |
| Mooncake Store | 共享对象池及其目录 | 对象按租约、副本和淘汰策略管理 | 查询副本位置，再传入引擎目标块 |
| LMCache MP | 引擎外的 LMCache Server 及配置的后端 | 保存的 KV 可跨请求复用 | 外部查询与恢复；跨服务器复用依赖共享配置 |

Mooncake 把集群贡献的内存和存储组织成对象池，Master 返回副本描述，数据面绕过 Master。LMCache MP 把缓存服务移出引擎进程，再通过 Connector 接入查找、保存与加载。两种架构都能扩展缓存容量，但调试时要分别检查对象目录或缓存服务的状态，以及引擎是否已收到可用数据。

### 计算命中与传输命中

**示例：P 命中前缀，D 没有对应 KV。**

假设一个请求的前 8,000 个 token 在 P 上已经缓存，后 2,000 个 token 需要计算：

- **P 的计算**：复用已有前缀，只计算未命中的部分。
- **D 的加载**：仍需要获取生成阶段所依赖的全部历史状态。

P 的计算量下降，并不保证 P→D 的交接量同比下降。

反过来，如果 D 已持有可复用的前缀，且 Connector 支持识别并跳过这些块，才可能减少本次加载量。[vLLM NIXL Pull Scheduler](https://github.com/vllm-project/vllm/blob/7a64fb8fc9239cb65e0df9313fa759594dfb206a/vllm/distributed/kv_transfer/kv_connector/v1/nixl/pull_scheduler.py) 会结合 D 的本地已计算 token 数确定外部加载范围；完全本地命中时仍需通知源端释放本次交接所保留的状态。

因此，缓存指标至少要区分 **P 的计算命中、D 的本地命中和外部层级命中**。用一个“命中率”同时推算 Prefill FLOPs、网络流量与 Decode 容量，会掩盖它们发生在不同位置这一事实。

### 失败清理的边界

一次交接中，源块可能被发送任务引用，目标块可能已经分配，存储副本也可能仍被租约保护。客户端取消请求后，这些资源需要分别结束自己的使用关系。通信超时只能说明等待超过期限；释放或复用远端可写内存之前，还需要确保旧操作不会继续访问它。

错误也需要保留语义差异：可复用前缀不存在时，可以按缓存未命中处理；已承诺的 PD 交接失败时，则要遵循后端的加载失败策略。LMCache MP 的示例将 NIXL 加载失败设为 `fail`，而其 L2 适配器对失败与未命中的区分又不同。统一写成“传输失败就本地重算”会遗漏 Decode-only 部署和已提交请求的限制。

## 请求协调与 Worker 选择

### Dynamo 的 Prefill-first 路径

[Dynamo 集成 Frontend 的分离式路由](https://github.com/ai-dynamo/dynamo/blob/3032e8a703e5680d7481b9e499a6f979ed37bba1/docs/fern/pages/developer-guide/knowledge-base/modular-components/router/disaggregated-serving.md) 在发现匹配的 P、D 服务后，启用内部 Prefill Router。请求经预处理后先选 P；P 返回交接元数据，再进入 Decode 路由，把元数据交给选中的 D。

这个路径把缓存复用决策主要放在 P 侧。文档对应的分离模式关闭 D 路由的 overlap 评分，避免在已完成 Prefill 后继续追逐 Decode 前缀复用。P、D 跨机架或区域时，P 的位置还可以约束后续 D 的候选范围，使路由考虑 KV 传输拓扑。

原书的 Decode-centric 流程图描述另一种协调顺序，不能直接作为所有 Dynamo 版本的执行图。在上述集成路径中，请求一旦已分派给 P，Prefill 或交接失败会返回错误；不存在自动改走聚合 Decode 路径的通用保证。

### llm-d 的 Decode 侧协调

[llm-d 的分离式服务设计](https://github.com/llm-d/llm-d/blob/d5e53624ca354290b48323a3786b4a9bba836e0b/docs/architecture/disaggregation/pd-disaggregation.md) 把选择与执行拆开：Endpoint Picker（EPP）选定实例，D Pod 前面的 Routing Sidecar 协调请求的两个阶段。

<Frame caption="来源：[llm-d PD Disaggregation 架构图](https://github.com/llm-d/llm-d/blob/d5e53624ca354290b48323a3786b4a9bba836e0b/docs/assets/pd-disaggregation.svg)。">
  <img src="/books/ai-systems-performance-engineering/images/ch17-llmd-pd.svg" alt="llm-d 中网关、EPP、Decode Sidecar 与 Prefill/Decode Worker 的连接关系" />
</Frame>

`disagg-profile-handler` 按以下顺序选择实例：

1. **选择 D**：运行 Decode profile，确定目标 Decode 实例。
2. **判断是否分离**：decider 根据已选 D 上未缓存的 prompt 部分，决定是否选择远端 P。
3. **按需选择 P**：需要分离时运行 Prefill profile，将 P、D 地址一起交给代理。

这个顺序让“是否远程 Prefill”可以利用已选 D 的缓存信息；省略 P 的路径要求目标实例具备相应执行能力。

在 vLLM/NIXL 路径中，Sidecar 先请求 P，获得 `KVTransferParams` 后再调用 D，由 D 拉取 KV。SGLang 的交接路径则使用 bootstrap 信息协调 P、D，可并发发起两侧请求。Sidecar 的控制顺序要适配引擎协议，不能只把后端名称替换掉。

| 比较点 | Dynamo 集成 Prefill-first 路径 | llm-d 分离 profile |
| --- | --- | --- |
| Worker 选择顺序 | P 后 D | 先 D，再决定是否选 P |
| 跨阶段协调位置 | Frontend 与内部路由阶段 | D Pod 的 Routing Sidecar |
| 缓存决策位置 | P 的前缀复用；该模式 D overlap 评分关闭 | decider 可以使用已选 D 的未命中部分 |
| 关键约束 | 已派发 P 后的错误不能假定自动本地回退 | Sidecar 请求顺序取决于后端交接协议 |

## 缓存局部性与负载感知路由

### Dynamo 与 vLLM 的事件索引

[Dynamo Router](https://github.com/ai-dynamo/dynamo/blob/3032e8a703e5680d7481b9e499a6f979ed37bba1/docs/fern/pages/developer-guide/knowledge-base/modular-components/router/router-design.md) 可以通过引擎发布的 KV stored/removed 事件维护缓存位置索引。vLLM 持有真实 KV 块，路由侧维护“哪些前缀可能在哪些 Worker 或介质上复用”的视图，再将重叠收益与活跃负载组合成路由评分。

对两个候选 P，缓存更多的一侧未必更早完成。某个 Worker 若少算 4,000 个 token，却需要额外排队 300 ms，而另一个空闲 Worker 只需 100 ms 完成这些计算，最长前缀匹配就不是更好的选择。这是一个决策示例，实际计算时间需要由对应模型和硬件的观测估计。

缓存事件存在传播延迟，路由副本之间的负载状态也可能不同。KV 已被淘汰但 Router 尚未处理 remove 事件时，路由命中仍需要由引擎实际查找结果确认。Dynamo 也提供近似模式；事件索引是特定部署方式，不能作为所有配置的前提。

### SGLang Router 的近似 Radix 索引

Radix Tree 将共享前缀压缩到共同路径，分叉处保存不同后缀。它既可以索引引擎内的可复用 KV，也可以只记录路由历史；数据结构相似，并不代表索引中的数据同样真实。

[SGLang Gateway 的 `CacheAwarePolicy`](https://github.com/sgl-project/sglang/blob/406786fd910dd82d03d1ce2c2e4c08b547786bc2/sgl-model-gateway/src/policies/cache_aware.rs) 用请求文本与历史 Worker 分配维护近似前缀信息，以此预测再次路由到某个 Worker 的缓存收益。这个策略无需每次查询 Worker 的完整 KV 状态，但请求曾经到过某个 Worker，并不能保证相应 KV 现在仍在 HBM 中。

该实现先判断负载是否明显失衡：绝对负载差和相对比例同时越过阈值时，优先选择低负载实例；负载较平衡时，使用前缀匹配和阈值选择实例，匹配不足时转向最小负载。具体行为以链接中的策略实现为准，不把它推广到 SGLang 的所有路由模式。

| 维度 | Dynamo 的 KV 事件模式 | SGLang `CacheAwarePolicy` |
| --- | --- | --- |
| 缓存信息来源 | 引擎或缓存层报告的状态变化 | Router 观察到的请求与分配历史 |
| 维护成本 | 发布、订阅、索引更新与恢复 | 维护近似前缀树和 Worker 状态 |
| 误差来源 | 事件延迟、丢失或索引重建 | 历史分配与真实淘汰状态不一致 |
| 负载权衡 | 缓存收益与活跃负载共同参与评分 | 明显失衡时先避开高负载，平衡时利用前缀匹配 |

以 vLLM 为主的系统可以使用 Dynamo 的事件路由；SGLang 在这里提供的是另一种获取缓存位置的机制。二者的比较重点在信息成本与误差，而不是把 Radix Tree 当成某一个引擎独有的能力。

## 双池容量、弹性与过载控制

### Dynamo Planner 的两个时间尺度

<Frame caption="原书图 17-7，用于说明双池容量随输入、输出需求变化；当前控制流程见 [Dynamo Planner Design](https://github.com/ai-dynamo/dynamo/blob/3032e8a703e5680d7481b9e499a6f979ed37bba1/docs/fern/pages/developer-guide/knowledge-base/modular-components/planner/planner-design.md)。">
  <img src="/books/ai-systems-performance-engineering/images/ch17-figure-7.png" alt="Planner 随工作负载调整 Prefill 与 Decode 资源池比例" />
</Frame>

Dynamo Planner 使用两个时间尺度的控制：

- **Throughput-based 预测**：使用流量、输入输出长度及性能模型估计容量需求，调整周期较慢。
- **Load-based 修正**：使用当前前向执行指标、队列与 Worker 状态调整副本数，更快响应实时负载。

两者同时启用时，预测路径给出**副本数下界**，负载路径可以在其上扩容，避免短暂空闲立即抵消为后续流量准备的容量。

两个池需要不同的工作量描述。Prefill 容量受未命中输入 token 和计算形态影响；Decode 容量还受活跃序列、上下文长度、KV 占用和迭代延迟影响。单看 GPU Utilization 无法判断到底应该扩哪一侧。

在固定长度分布下，可以把各阶段能力折算为请求速率，得到容量上界：

$$
R_{system} \leq \min(R_P, R_D, R_{handoff})
$$

实际 goodput 还受排队、尾延迟与容量碎片限制。若瓶颈在 Decode 或 KV 交接通道，继续扩 Prefill 只会加快产生等待中的状态。扩容生效前还存在权重加载与预热时间，因此短时过载不能完全依靠新增副本消化。

### Mooncake 的预测性提前拒绝

[Mooncake 论文](https://arxiv.org/abs/2407.00079) 从资源受限下的过载出发：如果请求完成 Prefill 后没有满足延迟目标的 Decode 容量，已经投入的 Prefill 计算和 KV 传输可能无法产生有效结果。其 early rejection 策略尝试在投入这部分资源前，预测请求进入 Decode 时的负载并决定是否接纳。

只根据当前 D 是否繁忙拒绝请求，反馈会滞后于 Prefill 的执行时间：一段时间内大量拒绝使后续 Decode 供给不足，随后又集中接纳。论文因此讨论基于未来负载预测的拒绝策略。这是对固定容量的接纳控制，与 Planner 改变副本数量的控制作用不同。

当前开源 [Mooncake Conductor](https://github.com/kvcache-ai/Mooncake/blob/6a835cbf934aa50c287261f255c83e6faffecb71/docs/source/design/architecture.md) 提供全局前缀索引和查询服务；不能把论文中完整的调度与拒绝策略视为安装 Transfer Engine 或 Store 后自动获得的行为。

| 控制机制 | Dynamo Planner | Mooncake 论文的 early rejection |
| --- | --- | --- |
| 主要动作 | 调整 P、D 副本目标 | 决定单次请求是否进入后续处理 |
| 生效条件 | 有可用资源，且新副本能完成加载与准备 | 有可用于判断未来可服务性的负载估计 |
| 解决的问题 | 持续需求变化与两池容量失衡 | 容量暂时不足时减少无效计算 |

## 多模态 EPD 分离

### 编码池与 Embedding 交接

[Dynamo 的 Encoder Disaggregation](https://docs.nvidia.com/dynamo/v1.2.1/user-guides/multimodal/encoder-disaggregation) 将视觉编码从语言模型执行路径移到独立 Encode Worker。E 计算图像 embedding，再交给下游语言模型；P 完成 prompt 计算并把 KV 交给 D。两次交接的对象和消费者不同。

<Frame caption="来源：[NVIDIA Dynamo — EPD Disaggregation for Multimodal Inference](https://docs.nvidia.com/dynamo/dev/digest/epd-disaggregation-multimodal)。图中的 embedding 缓存与请求关系对应该文描述的路径。">
  <img src="/books/ai-systems-performance-engineering/images/ch17-epd.webp" alt="从聚合多模态推理拆分为 Encode、Prefill、Decode，并在 embedding 缓存未命中时请求编码服务" />
</Frame>

| 部署形态 | Worker 划分 | 主要跨 Worker 状态 |
| --- | --- | --- |
| E/PD | 独立 E；P 与 D 共置 | E→PD 的 embedding |
| E/P/D | E、P、D 分别独立 | E→P 的 embedding；P→D 的 KV |

以 Dynamo + vLLM 为例，独立 E 可以随图像请求量扩容，语言模型池按文本与视觉 token 的计算需求扩容。图像占比增加时，扩 E 可以缓解编码排队；若瓶颈已转移到 P 或 D，继续扩 E 就只会增加下游到达压力。是否使用较小 GPU 承担 E，还需要核对编码模型容量和 embedding 传输开销。

### Worker 划分与硬件放置

Worker 拆分也不要求每个角色独占 GPU。Dynamo 的 EPD 分析比较了两种放置方式：

- **共享 GPU**：编码 Worker 与语言模型 Worker 分开队列和批处理，仍共享设备算力。
- **独立硬件层**：编码 Worker 使用单独的设备，增加资源隔离，也增加独立硬件成本。

选择取决于编码占比、生成长度和可用硬件，不能只按 Worker 数量判断隔离程度。

### Embedding 与 KV 的复用范围

Embedding Cache 与 KV Prefix Cache 也需要分开统计。前者复用视觉编码结果，后者复用语言模型在具体上下文中形成的状态；相同图片放进不同 prompt，并不自动构成完整的语言模型前缀命中。图中先查 embedding cache、未命中再访问 E 的做法，可以避免重复编码，但 P 仍需完成尚未复用的语言模型计算。

支持范围随后端与版本变化。例如上述 v1.2.1 文档中，vLLM 独立 E 处理 `image_url`，`video_url` 留在 P/PD 路径；不能把“三池部署”直接推导为所有多模态输入都已支持独立编码。

## Attention–FFN 分离

### vLLM AFD Plugin 的执行契约

AFD 沿模型层内的 Attention 与 FFN 边界拆分执行。Attention 侧保存历史 KV，并产生送往 FFN 的 hidden states；FFN 处理后返回输出，供后续计算继续使用。PD 按请求阶段划分，AFD 按层内算子划分，两种拆分可以组合。

<Frame caption="来源：[vLLM AFD Plugin 官方介绍](https://vllm.ai/blog/2026-07-23-vllm-afd-plugin)。图展示插件总体架构，兼容性以对应源码版本为准。">
  <img src="/books/ai-systems-performance-engineering/images/ch17-vllm-afd.svg" alt="vLLM AFD Plugin 中 Attention、FFN Worker 和 Connector 的关系" />
</Frame>

[AFDConnectorBase](https://github.com/vllm-project/afd-plugin/blob/bcc012632576abe34243d1373a157c896b339264/afd_plugin/connectors/base.py) 定义 `send_attn_output`、`recv_ffn_output` 等接口，传递 hidden states 以及层、阶段、token 布局等上下文。[AFDFFNWorker](https://github.com/vllm-project/afd-plugin/blob/bcc012632576abe34243d1373a157c896b339264/afd_plugin/v1/worker/ffn_worker.py) 不分配 KV Cache，其工作由 Connector 元数据驱动。

两种 Connector 对接的执行边界不同：

- **KVConnector**：对接请求调度、块分配与外部缓存。
- **AFD Connector**：对接模型逐层执行，在 Attention 与 FFN rank 之间交换激活。

将两个组件都称为 Connector，并不代表能用同一套数据格式或完成事件替换。

插件使 Attention 与 FFN 可以采用不同的资源和并行组织。Attention 一侧需要兼顾 KV 容量与访问局部性，FFN/MoE 一侧需要考虑计算批量和专家分布；把两个池拆开后，任一侧排队都会反映到逐层等待时间中。

<Note>
[插件 README](https://github.com/vllm-project/afd-plugin/blob/bcc012632576abe34243d1373a157c896b339264/README.md) 明确标注**实验状态**。所核对快照的 GPU 目标版本为 **vLLM 0.30.0**，部署兼容性需按对应版本确认。
</Note>

### 每 Token 的通信预算

PD 的主要 KV 交接发生在 P→D 阶段边界；AFD 在每个参与拆分的层交换激活。Decode 每生成一个 token 都要重复这些层内依赖，因此小消息延迟、同步和排队会直接影响 TPOT。

以某一层为例，Attention 输出完成后，需要经历发送、FFN 排队与计算、结果返回，才能继续依赖该结果的计算。微批流水线或 Dual Batch Overlap 可以将一个微批的等待与另一个微批的计算重叠，但可隐藏的时间受可并行工作、依赖关系和批量限制。不能把“使用 DBO”直接写成“通信开销归零”。

[FastAFD 解读](https://princepride.github.io/live-streaming-tools/fastafd_vllm_plugin/final/blog/) 提供了插件与重叠执行的图解。判断方案收益时，还需结合实际硬件、模型、微批划分、专家负载和源码支持范围；官方博客中的特定 benchmark 也不能替代完整模型与真实请求分布下的验证。

### NVIDIA GPU 与 LPU 的异构 Decode

<Frame caption="来源：[NVIDIA — Inside NVIDIA Groq 3 LPX](https://developer.nvidia.com/blog/inside-nvidia-groq-3-lpx-the-low-latency-inference-accelerator-for-the-nvidia-vera-rubin-platform/#decode_phase_a_repeated_multi-engine_loop)。">
  <img src="/books/ai-systems-performance-engineering/images/ch17-lpx-decode.webp" alt="GPU 读取 KV 并执行 Attention，LPU 执行 FFN 或 MoE，每个 token 在两类引擎间循环交换激活" />
</Frame>

NVIDIA 描述的异构 Decode 路径让 GPU 持有 KV 并执行 Attention，LPU 执行 FFN/MoE，两侧交换中间激活。图中的循环发生在逐 token 的模型执行过程中，适合说明 AFD 的硬件映射：历史状态留在 Attention 侧，另一类设备承担 FFN 计算。

这是厂商公布的系统架构描述，与 vLLM AFD Plugin 是两个不同层次的实例。前者说明异构硬件分工，后者给出可检查的 Worker 和 Connector 契约；不能据此声称该插件已经实现或验证了 GPU/LPU 路径。

## 架构验证的观测点

验证分离方案时，除了固定模型、总资源、请求分布和 SLO，还应记录跨边界的等待与状态占用。以下观测对应前述机制，避免把所有时间合并进一个 TTFT 或 TPOT：

| 机制 | 需要关联的观测 | 可定位的问题 |
| --- | --- | --- |
| PD 交接 | P 计算结束、D 分配完成、传输开始/完成、首轮 Decode | 接收端准备与实际数据传输谁在关键路径上 |
| 外部缓存 | 本地/外部命中 token、加载字节、恢复时间、重新计算量 | 命中是否真的减少请求完成时间 |
| 异步生命周期 | 计算结束后仍被引用的源块、未完成目标块、超时回收 | 传输拖延造成的容量占用或清理异常 |
| 缓存路由 | Router 预测命中、引擎实际命中、候选负载与最终排队 | 索引误差与负载权衡是否合理 |
| 双池控制 | 副本目标与 ready 数、P/D 队列、拒绝率、goodput | 扩容延迟、单侧瓶颈与过载反馈 |
| EPD | 编码排队、embedding 命中与传输、语言模型排队 | 独立 E 后瓶颈是否转移 |
| AFD | 逐层激活交换、FFN 等待、微批重叠与 TPOT | 通信和两侧排队是否抵消拆分收益 |

这些是验证方案需要采集的证据，并非本页已执行的实验结果。缓存布局、传输内核和 profile 方法可继续结合[第十八章：高级 Prefill-Decode 与 KV Cache 调优](/books/ai-systems-performance-engineering/chapters/ch18)与[第十六章：大规模推理的分析、调试与调优](/books/ai-systems-performance-engineering/chapters/ch16)展开。
